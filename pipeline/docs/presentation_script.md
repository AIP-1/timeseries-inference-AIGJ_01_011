## 1. 표지 — 교육장 CO₂를 60분 먼저 읽는다 `[0:00]`
안녕하세요, team4입니다. 저희는 교육장 CO₂·온도·습도 센서만으로 '지금 어떤가, 60분 뒤 어떻게 될까'에 답하는 서비스를 팀 Jetson에서 2주째 상시로 돌리고 있습니다. 무엇이 됐고, 무엇이 안 됐고, 왜 그런지 5분 동안 말씀드리겠습니다.

## 2. 구조 `[0:25]`
구조는 네 단계입니다. 수집기가 학원 브로커에서 센서값을 받아 Jetson에 쌓고, 과거 데이터로 학습한 모델을 ONNX로 바꾸고, 추론 서비스가 매분 예측·이상 탐지·사용 여부·환기 경보를 계산해 MQTT와 API로 내보냅니다. 지난 2주 수집 커버율은 99% 이상이었고, 그사이 보드가 네 번 재부팅됐는데도 빠진 데이터는 최대 7분이었습니다. 시험용 브로커를 껐다 켜면 12초 만에 다시 받습니다. 핵심은 학습과 서비스가 같은 전처리 코드를 쓴다는 점입니다.

## 3. 데이터 `[1:00]`
제공 키트를 받지 못해서, 과제 설명대로 합성 데이터 생성기를 직접 만들어 전 과정을 먼저 완성했습니다. 시간표에 따라 CO₂가 물리적으로 변하고, 마지막 주에는 정답을 아는 고장 10건이 들어 있습니다. 그다음 학원 InfluxDB에서 실데이터 14개월치를 받아 다시 검증했습니다. 실제 시간표는 없어서 학습 기간 데이터로 추정했습니다.

## 4. 결과표 `[1:35]`
결과입니다. 수집, 이상 탐지, 서비스는 기준을 넘었습니다. 환기 경보는 처음 재현율 84.2%로 0.8%p 모자랐는데, 분류기와 예측 모델 중 하나라도 경보를 내면 알리도록 바꿔 86.7%가 됐습니다. 이 방법은 검증 기간으로만 골랐고 임계값은 다시 고르지 않았습니다. 실데이터 60분 예측은 모델 앙상블로 9%에서 15%까지 올렸지만 30% 기준에는 못 미쳤습니다. 서비스가 2주 동안 실제로 낸 예측을 채점하면 17% 개선입니다.

## 5. 가장 의외였던 발견 `[2:15]`
가장 의외였던 건 예측을 가른 게 모델이 아니라 시간표였다는 점입니다. 진짜 시간표가 있는 합성 데이터에서는 일정 정보가 오차를 27% 줄였지만, 추정 시간표뿐인 실데이터에서는 4%에 그쳤습니다. 모델을 바꾸거나 섞어서 얻은 건 3~4ppm입니다. 실데이터 오차는 아침 8시에 몰리는데, 이때는 '현재값 유지'보다도 나쁩니다. 오늘 정말 수업이 있는지를 모델이 모르기 때문입니다.

## 6. 실데이터 하루 (10-14) `[2:50]`
실제 하루를 보면 이유가 보입니다. 10월 14일 수요일입니다. 사무실은 모델이 아침 상승과 오후 고점을 기준선보다 먼저 따라갑니다. 그런데 실습실은 9시 반에 1,150ppm을 예측했지만 실제로는 820에서 멈췄고, 회의실은 아무도 없었는데 10시에 1,160ppm으로 헛예측했습니다. 평소 패턴은 배웠지만, 그날 실제로 수업이나 회의가 있는지는 알 방법이 없습니다.

## 7. 이상 탐지 · 환기 경보 `[3:20]`
이상 탐지는 세 가지를 합쳤습니다. 오토인코더는 냉방 정지를, 규칙은 튄 값과 값 고정을, 예측 오차는 환기 정지를 잘 잡아서 고장 10건을 모두 잡았습니다. 실운영 2주 동안 1,000ppm을 넘은 25번 중 24번은 10분 이상 먼저 경보가 났습니다. 다만 경보의 정밀도가 8~31%라 헛경보가 많습니다. 이게 다음 과제입니다.

## 8. 엣지 최적화의 함정 `[3:55]`
보드에서는 작은 모델일수록 호출 비용이 커서 ONNX Runtime CPU가 0.3ms로 가장 빨랐고, 서비스 전체가 112MB만 씁니다. TensorRT 반정밀도는 GRU에서 반올림 오차가 쌓여 1.5ppm으로 기준을 넘었습니다. 그런데 FP32로 만든 엔진도 1ppm 가까이 달랐습니다. Orin GPU가 행렬 곱을 기본으로 TF32로 하기 때문이었고, 옵션 한 줄로 끄자 0.001ppm이 됐습니다. 다만 미리 정한 선택 규칙은 0.003ms 빠른 TF32 엔진을 골랐고, 그 엔진은 시험에서 1.002ppm으로 아주 조금 넘었습니다. 그대로 보고했습니다.

## 9. 다음 할 일 `[4:35]`
다음 할 일입니다. 첫째, 실제 수업 시간표와 회의실 예약을 받아 예측 입력으로 넣는 것, 이게 30% 기준을 넘는 열쇠입니다. 둘째, 서비스가 11월 들어 스스로 성능 저하 경보를 내고 있어서, 새 데이터로 다시 학습하는 것입니다. 셋째, 환기 경보 정밀도를 높이는 것, 넷째, 다음 주 로컬 LLM 에이전트가 우리 API를 도구로 쓰게 연결하는 것입니다. 감사합니다.

## 예상 질문과 답
- **왜 실데이터 예측이 기준에 못 미쳤나?** 실제 시간표·예약이 없어서입니다. 오차가 아침 8시에 몰리고, 합성 데이터에서 일정 정보만으로 27%가 줄었습니다. 모델 종류·앙상블 효과는 3~4ppm이었습니다.
- **앙상블은 시험 결과를 보고 고른 것 아닌가?** 아닙니다. 후보 4개를 검증 기간(9월) 오차로 골랐습니다. 시험(10월)은 고른 뒤 한 번 계산했습니다.
- **환기 경보 기준을 바꾼 적이 있나?** 처음 MLP 임계값을 고를 때 한 번 있습니다. 검증 재현율 85%에 맞추자 시험에서 81.6%가 나와, 검증 기준을 90%로 바꿨습니다. 보고서에 밝혔습니다. 이번 재시도에서는 임계값을 그대로 두고, 예측 모델 경보를 더하는 방법을 검증 기간으로 골랐습니다.
- **합성 데이터는 믿을 만한가?** 키트 대신 과제 설명대로 만든 것이라 '우리가 생각한 세계에서의 성적'입니다. 그래서 과제 2·3·6·7·8은 실데이터로 다시 돌렸습니다.
- **왜 TensorRT를 안 쓰나?** 이 모델 크기에서는 ONNX Runtime CPU가 더 빠르고(0.32ms vs 0.48ms) 오차도 0에 가깝습니다. GPU는 같은 보드의 LLM에 양보합니다.
- **결측은 왜 생겼나?** 첫날 메모리 부족 재부팅(23분, 스왑 추가로 해결) 말고는, 2주 동안 전체 끊김이 5분 이하였습니다. 재부팅 때 끊긴 동안의 메시지는 브로커가 세션을 기억해 다시 보내 줍니다.
